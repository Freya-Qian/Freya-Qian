# 第 2 阶段技术开发文档｜M2 竞品证据与定位

> ⚠️ 本文档为历史版本。2026-09-22 按《竞品抓取能力升级方案》已调整：WorkBuddy 彻底移除（竞品由用户自选 ≤3 个）、多竞品对比表、贴网址抓取。以下内容中涉及“WorkBuddy/示例模板”的表述已被后续方案取代。

> 配套文档：PRD V1.0、技术适配声明、通用技术栈手册。
> 本文档只覆盖 M2（竞品证据 + 定位与差异点）；M3 PRD/任务拆解、M4 资料包导出为后续子阶段，本阶段不提前实现。

## 一、阶段目标
- 交付范围（对齐 PRD 4.4/10.3/10.4/11.4）：内置 WorkBuddy 已核查证据卡 → 新增/删除竞品与证据卡（source_url 必填校验）→ 对比表 → 产品定位与差异点（每个差异点有证据引用）→ 确认后进入 PRD 阶段。
- 阶段产物：竞品证据库 + 定位与差异点（后端 API + 验收界面 + SQLite 持久化）。
- 验收标准（对齐 PRD 10.3/10.4）：
  - 默认生成 WorkBuddy 对比表，维度含定位/用户/场景/流程/输出物/协作/集成/差异机会；
  - 每条证据卡含 source_url、结构化结论、启发；
  - 定位不是泛泛的"AI 工作台"，每个差异点至少引用 1 条证据。
- 明确不做：PRD 生成/证据引用审计全量（M3）、任务拆解（M3）、资料包导出（M4）、竞品自动抓取（V1）。
- 主链路：需求摘要确认 → 查看 WorkBuddy 证据卡 →（可新增/删除证据）→ 生成定位与差异点 → 编辑/确认 → 进入 PRD。

## 二、技术适配摘要
- 沿用纵向切片路径 B，M2 复用 M1 的 Task 异步框架、LLMClient、parser、验收界面骨架。
- 本阶段启用：SQLite 新表（Competitor/CompetitorEvidence/Positioning）、证据引用校验（确定性代码）。

## 三、技术栈与模型
- 同 M1：FastAPI + SQLite/SQLAlchemy + qwen-plus（定位生成，temperature 0.5，超时/重试兜底）。
- 不引入新组件。

## 四、环境与配置
- 无新增配置。后端仍 8200；数据库新增 3 张表（create_all 幂等建表）。

## 六、数据、资产与状态
- 新表：competitors（默认 WorkBuddy，is_default）、competitor_evidences（ref_key 供引用、source_url 必填、confidence/evidence_type 枚举、used_in 引用状态）、positionings（differentiators/comparison/evidence_refs 存 JSON 文本）。
- 状态机：Project.current_stage：competitor（本阶段起点，摘要确认后）→ prd（定位确认后，M3）。
- 证据引用：定位生成的 evidence_refs 只保留真实存在的 ref_key（确定性校验，不编造）；被引用的证据卡 used_in 标记"定位"。

## 七、API / 工具设计
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /projects/{id}/competitors | 竞品列表（懒种子化 WorkBuddy） |
| POST | /projects/{id}/competitors | 新增竞品 |
| GET | /projects/{id}/competitors/{cid}/evidences | 证据卡列表 |
| POST | /projects/{id}/competitors/{cid}/evidences | 新增证据卡（source_url 必填 + http/https 校验） |
| DELETE | /projects/{id}/competitors/{cid}/evidences/{eid} | 删除证据卡（UI 二次确认） |
| POST | /projects/{id}/positioning | 生成定位与差异点（异步，202 → task_id） |
| GET | /projects/{id}/positioning | 最新定位 |
| PUT | /projects/{id}/positioning | 编辑；confirm=true 确认并进入 PRD |

## 八、Prompt 设计
- `POSITIONING_SYSTEM`：要求明确"Web 端 + 产品孵化"、每个差异点至少引用 1 个 ref_key、evidence_refs 只能填输入中真实存在的 ref_key、证据不足标"待补证"、对比表至少覆盖 8 维度。
- 格式三件套：Prompt 给 JSON 格式与约束 → parser 括号配对扫描 → 引用校验只保留真实 ref_key（数量约束不遵守记瑕疵，不重试）。

## 九、验收界面
- 界面新增第 4 步（竞品证据：查看 WorkBuddy 证据卡、新增/删除证据）与第 5 步（定位与差异点：生成、查看对比表、编辑、确认）。

## 十、测试要求
- mock 自动化测试：36/36 通过（M1 27 + M2 9：种子化/幂等/新增竞品/source_url 校验/增删证据/定位需摘要/定位生成/确认推进/used_in 标记）。
- 真实模型冒烟：见 evidence/阶段2-M2/真实冒烟输出.txt（定位生成成功，对比表覆盖 8 维度、证据引用 WB-E1/E3/E4 正确、协作项诚实标"待补证"）。

## 十一、验收清单（照着点）
1. 打开 http://127.0.0.1:8200/ ，选一个已完成需求澄清的项目（或新建走完第 2-3 步）。
2. 第 4 步「刷新竞品证据」→ 看到 WorkBuddy + 6 张证据卡（含 source_url、置信度）。
3. 可新增一条证据卡（填 source_url）或删除一条（二次确认）。
4. 第 5 步「生成定位与差异点」→ 看到一句话定位、差异化（含证据引用）、对比表、不做什么。
5. 编辑 →「保存并确认」→ 项目阶段变 PRD。

## 十二、风险与待确认项
- WorkBuddy 作为默认竞品对"番茄钟"这类非办公类想法，对比略显牵强（PRD 10.1 固定默认竞品所致）；用户可新增更相关的竞品。此为 PRD 既定设计，不在本阶段变更。
- 真实冒烟一次定位生成约 20s，满足 PRD 17.1（≤3min）。

## 十三、交接给下一阶段

- M2 已就绪复用件：证据卡 ref_key 引用体系、used_in 标记、Positioning 结构化产物、Task 异步框架。
