# 第 2 阶段技术开发文档｜M1 项目与需求澄清

> 配套文档：PRD V1.0、技术适配声明、AI 产品 Vibe Coding 通用技术栈手册。
> 本文档只覆盖 M1（项目与需求澄清）；M2 竞品证据/定位、M3 PRD/任务拆解、M4 资料包导出为后续子阶段，本阶段不得提前实现。

## 一、阶段目标
- 交付范围（对齐 PRD 10.1/10.2/11.1-11.3）：新建项目（含 3 示例想法 + goal_type + 默认竞品）→ 8 问需求澄清（首轮 1 轮、可跳过；第 2 轮后置，后续迭代补齐）→ 结构化需求摘要（可编辑、可确认）→ 确认后进入竞品证据阶段。
- 阶段产物：可独立运行的后端 API + 最小 HTML 验收界面 + 数据持久化（SQLite）。
- 验收标准（对齐 PRD 10.1/10.2）：
  - 1 分钟内创建项目；创建后自动进入需求澄清；列表展示阶段与更新时间。
  - 输入一句模糊想法后生成 ≥8 个针对性问题；回答后生成结构化摘要；摘要可编辑、可确认。
- 明确不做：竞品证据卡/定位（M2）、PRD/任务拆解（M3）、资料包导出/迭代记录（M4）、账号登录、飞书/GitHub 真实 API 同步、竞品自动抓取（均后置）。
- 本阶段打通的主链路：新建项目 → 生成 8 问 → 回答 → 生成需求摘要 → 编辑/确认 → current_stage 推进到 competitor。

## 二、技术适配摘要
- 引用《技术适配声明》结论：纵向切片路径 B，拆 M1-M4。
- 本阶段采用默认方案：Python + FastAPI + Pydantic + pytest + SQLite/SQLAlchemy。
- 本阶段启用按需模块：SQLite+SQLAlchemy（多实体）、持久化任务记录（异步 LLM 任务）、最小 HTML 验收界面。
- 本阶段偏离/暂缓：Alembic（用 create_all）、SSE（问题/摘要用"提交+轮询"，流式到 PRD 生成阶段再评估）、正式前端三栏工作台（阶段 3）、第 2 轮追问（首轮 1 轮，第 2 轮后置后续迭代，PRD"最多 2 轮"作为最终目标保留）。

## 三、技术栈与模型
- FastAPI 0.115.6 / SQLAlchemy 2.0.36（SQLite）/ Pydantic 2.10.4 / httpx（LLM 调用）/ pytest。
- 模型：阿里云百炼 DashScope `qwen-plus`（OpenAI 兼容），用户自备 Key；超时 120s、重试 2 次；单项目预算软护栏 ≤10 元（配置项 PROJECT_BUDGET_CNY，本阶段先落配置、超限提醒逻辑到 M3 计费统计时实现）。
- 本阶段不引入：向量库、任务队列、对象存储、前端脚手架。

## 四、环境与配置
- 配置（`.env`，不含秘密的模板见 `.env.example`）：MODEL_API_KEY / MODEL_BASE_URL / MODEL_NAME / MODEL_TIMEOUT / MODEL_MAX_RETRIES / PROJECT_BUDGET_CNY / DEV_MODE。
- 用户提供：模型 API Key（验收前填到 `projects/AI产品工厂/.env` 的 MODEL_API_KEY）。
- 端口：后端 **8200**（与「脑洞游戏」8000、「AI Avatar Twin」8100 隔离）；数据库 `backend/data/product_factory.db`（已 gitignore）。

## 六、数据、资产与状态
- 持久化：SQLite（`backend/data/product_factory.db`），SQLAlchemy create_all 建表，重启可恢复。
- 数据表：users（预埋 local_user）、projects、clarification_qa、requirement_briefs、tasks。
- 状态机：
  - Project.current_stage：clarify（本阶段起点）→ competitor（摘要确认后，M2 起）。
  - Project.status：active。
  - RequirementBrief.status：draft → confirmed。
  - Task.status：queued → processing → success / failed（启动时把中断的 queued/processing 标 failed，由用户重试，不自动重做）。
- 资产：本阶段无图片/音频/视频资产。

## 七、API / 工具设计
统一错误：`{"error":{"code","message"}}`；code→HTTP 状态集中定义在 `core/llm.py`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/v1/samples | 冷启动示例想法 + goal_type |
| POST | /api/v1/projects | 创建项目（name/idea/goal_type），201 |
| GET | /api/v1/projects | 项目列表（按更新时间倒序） |
| GET | /api/v1/projects/{id} | 项目详情 |
| POST | /api/v1/projects/{id}/clarify/questions | 提交生成 8 问任务，202 返回 task_id |
| GET | /api/v1/projects/{id}/clarify/questions | 当前问题列表 |
| POST | /api/v1/projects/{id}/clarify/answers | 提交回答（answer 留空=跳过） |
| POST | /api/v1/projects/{id}/brief | 提交生成摘要任务，202 返回 task_id |
| GET | /api/v1/projects/{id}/brief | 最新摘要 |
| PUT | /api/v1/projects/{id}/brief | 编辑摘要；confirm=true 时确认并推进到 competitor |
| GET | /api/v1/tasks/{task_id} | 轮询任务状态 |

- 长耗时接口采用「提交 + 轮询状态 + 取结果」（非 SSE），任务状态先落库、崩溃可恢复。
- 8 问生成兜底：模型输出缺维度时用确定性默认问题补齐，保证 ≥8 问（PRD 10.2）。

## 八、Prompt 设计
- 8 问生成：`CLARIFY_SYSTEM`（8 维度各 1 问 + JSON 输出格式 + 正反例），`temperature=0.6`。
- 摘要生成：`BRIEF_SYSTEM`（10 字段 JSON 输出 + 未回答写"待确认"），`temperature=0.5`。
- 格式约束三件套：Prompt 明确 JSON 格式与禁例 → parser 宽容解析（容忍代码块/杂文）→ 数量约束（≥8 问）用兜底补齐而非重试。

## 九、验收界面或纵向切片
- `backend/app/static/index.html`：单文件原生 JS + fetch，挂 FastAPI 静态目录。支持：示例一键填入 → 创建项目 → 列表 → 生成 8 问 → 回答 → 生成摘要 → 编辑/确认。

## 十、测试要求
- mock 自动化测试：21 项全过（test_parser 5 / test_projects 5 / test_clarify 4 / test_brief 5 / test_llm_errors 2）。
- 真实模型冒烟：见「十二、验收清单」（无 Key 时该项待验）。

## 十一、验收清单（照着点）
1. 启动：`cd backend && .venv/bin/python -m uvicorn app.main:app --port 8200`，打开 http://127.0.0.1:8200/
2. 点示例按钮「番茄钟 App」一键填入 → 创建项目 → 列表出现该项目（阶段 clarify）。
3. 「生成澄清问题（8 问）」→ 出现 8 个问题，覆盖 8 个维度。
4. 逐个回答（可留空跳过）→「保存回答」。
5. 「生成需求摘要」→ 出现 10 字段摘要。
6. 修改任意字段 →「保存并确认」→ 显示"已确认"，列表阶段变为 competitor。

## 十二、风险与待确认项
- 真实模型冒烟待验：需产品经理在 `.env` 填 MODEL_API_KEY 后跑 5-10 条真实样例，按评分法定 D2/D3 验收标准。
- 单项目预算软护栏：本阶段仅落配置，超限提醒与 token 统计在 M3 引入（PRD 17.3）。
- 首轮问题生成时延 ≤15s、摘要 ≤3min：待真实模型实测确认（PRD 17.1）。
